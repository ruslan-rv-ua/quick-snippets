# DEVELOPMENT.md — Developer guide (Windows)

Коротко: цей репозиторій — Tauri 2 (Rust) backend + React/TypeScript frontend. Використовуйте `just` (PowerShell) або наведені нижче команди вручну.

## Prerequisites (Windows)

- Node.js (LTS; для тестів потрібна 22.22+, 24.15+ або 26+):
  - Scoop: `scoop install nodejs-lts`
  - або winget: `winget install OpenJS.NodeJS.LTS`
- Rust (rustup): `winget install --id Rustlang.Rustup` або з https://rustup.rs
  - MSVC toolchain: `rustup default stable-x86_64-pc-windows-msvc`
- Visual Studio Build Tools: workload "Desktop development with C++".
- WebView2 Runtime — уже є в Windows 10/11.
- just (рекомендовано): `scoop install just`.
- Tauri CLI окремо ставити не треба: він є в devDependencies, запускається через `npx tauri`.

## Команди just

`just` або `just help` показує всі рецепти. Основні:

```powershell
just setup             # npm install + перевірка Node/Rust
just dev               # Tauri dev: фронтенд + backend з hot-reload
just vite              # лише фронтенд (Vite dev server)

just test              # усі тести: Vitest + cargo test (однопотоково)
just test-front        # лише Vitest
just test-back         # лише cargo test
just test-mod db::tests  # один модуль Rust
just test-watch        # Vitest у watch-режимі
just test-cov          # Vitest з coverage

just check             # швидко: tsc --noEmit + cargo check
just lint              # tsc --noEmit + cargo clippy -D warnings
just format            # cargo fmt

just build             # debug-збірка (npm run build + cargo build)
just build release     # release-збірка через Tauri
just build-fast        # release-fast профіль: швидка компіляція, більший exe
just release           # tsc + release-збірка через Tauri

just final-checks      # version sync + tsc + clippy + тести + збірка
just db-reset          # видалити локальну quick-snippets-data\snippets.db
just clean             # видалити dist/ та src-tauri/target/
```

## Ручні (PowerShell) еквіваленти

```powershell
npm install                     # залежності
npx tsc --noEmit                # перевірка TypeScript
npx vitest run                  # тести фронтенду (одноразово)
npx vitest run src/hooks/__tests__/useSearchLogic.test.ts   # один файл
npm run test:rust               # тести Rust (--test-threads=1, через SQLite)
npm run test:all                # усі тести
npm run lint                    # tsc + clippy
npx tauri build --no-bundle     # портативний exe, як у релізі
```

Готовий exe: `src-tauri/target/release/quick-snippets.exe`.

## Перевірка з NVDA (smoke)

`just smoke` — перевірка зібраного exe разом з NVDA, триває близько двох з половиною хвилин. Скрипт
`scripts/smoke-nvda.ps1` натискає клавіші замість користувача, перевіряє результат кожного кроку
(через UI Automation, буфер обміну й реєстр) і показує, що NVDA сказав на кожному кроці.

- Спершу зберіть exe: `npx tauri build --no-bundle`.
- NVDA має бути запущений, рівень журналювання — «введення/виведення»
  (Налаштування NVDA → Загальні). Без NVDA перевіряється лише сама програма.
- Під час тесту не торкайтеся клавіатури й миші.
- Ваші дані не зачіпаються: тест запускає лише свою копію exe з тимчасової папки з порожньою
  базою. Запущену QuickSnippets скрипт закриває й назад не запускає; буфер обміну відновлює.
- Тека тестової копії називається `test copy`: у її шляху є пробіл. На рівень вище лежить ще одна
  копія exe, `test.exe`. Для запису автозапуску без лапок (`...\test copy\quick-snippets.exe`)
  Windows спершу спробувала б `...\test` і взяла б саме її. Крок увімкнення автозапуску перевіряє,
  що запис — шлях до тестової копії в лапках (REG_SZ, нічого після шляху), і створює з цього
  рядка процес так, як Windows читає командний рядок (`CreateProcess` без окремої назви
  програми), призупиненим: це має бути тестова копія, а не `test.exe`. Процес закривається до
  того, як почне працювати, тож жодна з копій при цьому не запускається.
- Автозапуск. Кожна копія QuickSnippets пише в реєстр два значення з тією самою назвою
  `QuickSnippets`: запис автозапуску (`HKCU\Software\Microsoft\Windows\CurrentVersion\Run`) і
  позначку Диспетчера завдань (`...\CurrentVersion\Explorer\StartupApproved\Run`). Тож тестова
  копія пише й видаляє значення вашої копії. Скрипт запам'ятовує обидва до тесту й наприкінці
  точно відновлює (тип і дані або відсутність значення); звіт показує їхній стан до тесту,
  наприкінці тесту й чи відновлено. Кроки автозапуску вмикають його (обидва значення: запис у
  лапках, див. попередній пункт, і позначка «увімкнено»), перевіряють, що зміна теми не чіпає позначку «вимкнено», записану так, як це
  робить Диспетчер завдань, і вимикають (обидва значення зникають). Якщо ваш запис автозапуску
  існує, ці кроки пропускаються, а тестова копія має лишити обидва значення як були.
- Наприкінці тест закриває свою копію через діалог виходу (Alt+F4, Ctrl+Enter) і запускає її
  знову з тією самою текою даних: так перевіряється, що тема й видалення зберігаються.
- Після цього перезапуску тестова копія працює зі змінною середовища
  `QUICK_SNIPPETS_TEST_AUTOSTART_ERROR=1` (лише вона: скрипт ставить змінну тільки на час
  запуску). Тоді програма вдає, що Windows не дозволила змінити «Запускати разом з Windows», і
  реєстру не чіпає. Наступні кроки разом зі зміною теми ставлять цей прапорець і зберігають:
  діалог має лишитися відкритим, прапорець — знятим і з фокусом, NVDA має один раз прочитати
  повідомлення, і ще раз після другого збереження; тема має зберегтися, а значення автозапуску в
  реєстрі — лишитися як були. Ламати справжній реєстр заради такої перевірки не можна: значення
  спільні для всіх копій програми.
- Тестова копія тримає дані вбудованого браузера в `quick-snippets-webview` у своїй тимчасовій
  папці. Останній крок перевіряє, що вони там, а не в `quick-snippets-data`, і що копія не
  змінила `%LOCALAPPDATA%\com.quicksnippets.app`, де їх тримають 0.3.3 і старіші. У тій теці
  скрипт читає лише кількість файлів і тек та час найновішої зміни, і лише коли інші копії
  програми закрито.
- Тому кожна тестова копія стартує з порожнім профілем браузера, як нова копія програми чи
  перший запуск після оновлення під Scoop. Для першого показу вікна це найважчий випадок (див.
  «Перший показ вікна після запуску» нижче), і тест перевіряє саме його. Якщо треба перевірити
  запуск із готовим профілем, є параметр `-BrowserProfileFrom <тека>`:
  `powershell -NoProfile -File scripts/smoke-nvda.ps1 -BrowserProfileFrom <тека>`, де тека —
  `quick-snippets-webview` копії, яку вже запускали й закрили (наприклад
  `src-tauri\target\release\quick-snippets-webview` після запуску зібраного exe). Скрипт
  копіює її поруч зі своєю тестовою копією.
- Поки програма схована, фокус стоїть у маленькому тестовому вікні скрипта, тож NVDA
  не читає ваших інших програм у звіт. З логу NVDA береться лише те, що записано під час тесту.
- Звіт друкується в консоль і зберігається в `%TEMP%\quick-snippets-smoke-report.txt`.
  Код виходу 0 — усе гаразд, 1 — є помилки.
- Перевірки «бажано» (наприклад, «Скопійовано») на результат не впливають: вікно ховається
  одразу після копіювання, і NVDA не завжди встигає це прочитати.
- `just smoke-tray` — той самий тест, але тестова копія стартує згорнутою в трей («Запускати
  згорнутим у трей» увімкнено), як після входу в Windows з автозапуском. Перший крок стежить за
  вікном від самого старту: воно не має з'явитися на екрані ні на мить, а NVDA не має сказати
  «QuickSnippets». Другий крок уперше показує вікно клавішами Ctrl+Alt+Space і вимагає, щоб NVDA
  одразу прочитав вікно й поле пошуку, один раз. Перезапуск наприкінці теж іде в трей і
  перевіряється так само, а після нього NVDA має назвати ще й перший сніпет. Параметр
  `-TrayIdleSec` (типово 5) — скільки секунд схована копія чекає перед клавішами. Запускайте
  після змін у створенні вікна, старті в треї чи показі вікна.
- Перший показ вікна після запуску обидва тести перевіряють так само суворо, як наступні: вікно
  й документ один раз, поле пошуку один раз і зі станами («можливо редагувати»), без фраз
  «веб-вміст» і адреси документа; у звичайному тесті перший Escape має сховати вікно.

### Перший показ вікна після запуску

NVDA читає вміст вбудованого браузера звичним способом (IAccessible2) лише тоді, коли його
допоміжна бібліотека вже під'єдналася до процесу браузера (`msedgewebview2.exe`); інакше бере
UI Automation. Під'єднується вона під час першої події фокуса, яку створює цей процес, тобто
саме тоді, коли вміст вікна вперше отримує клавіатуру. Поки процес браузера ще запускається
(на швидкому комп'ютері це перша секунда), NVDA встигає прочитати цю подію раніше. У звіті тоді
є «веб-вміст, регіон» чи «документ, http://tauri.localhost/», поле пошуку звучить двічі або без
станів, перший Escape забирає собі NVDA, і вікно ховається лише з другого. Від часу після
закриття попередньої копії це не залежить (так вважали до TASK-29), тож пауза між двома
запусками тесту для цього не потрібна.

Тому вікно завжди створюється схованим і без фокуса (`setup` у `src-tauri/src/lib.rs`; Tauri
саме його не створює: `"create": false` у `tauri.conf.json`). Зі стартом у треї воно таким і
лишається, доки користувач не попросить. Без нього вікно показує `finish_startup`: коли
сторінка повідомила, що готова (команда `frontend_ready`: список завантажено вже зі збереженими
темою, мовою й сортуванням), а якщо працює екранний диктор (прапорець Windows
`SPI_GETSCREENREADER`), то ще й після паузи. Пауза втричі довша за час від запуску до
готовності сторінки, але не менша за 1 с і не більша за 4 с (`src-tauri/src/startup.rs`).
Показ, про який попросили раніше (гаряча клавіша, трей, повторний запуск), чекає на цей
момент: усі способи показати вікно йдуть через `show_main_window`. Якщо сторінка не
повідомила про готовність за 3 с, запуск іде далі без неї.

Виміри TASK-29 (NVDA 2026.2, сторінка готова за 0,37 с після запуску): вікно, показане через
0,2 і 0,4 с після готовності, NVDA прочитав неправильно 4 рази з 4; через 0,6 с і більше —
правильно 9 разів із 9, з них 4 на навантаженому комп'ютері (раз із половиною зайнятих
процесорів, тричі з усіма).

Чого не робити:

- Не давати клавіатуру схованому вікну чи його вмісту, навіть на мить (була ідея так під'єднати
  NVDA заздалегідь). Щойно запущеній програмі Windows дозволяє вийти на передній план, тому
  сховане вікно стає активним і забирає клавіатуру, а NVDA читає вікно, якого немає на екрані.
  Так само поводиться вікно, створене лише схованим: вбудований браузер бере фокус під час
  створення, тому воно ще й «без фокуса». А якщо сховане вікно лишається з клавіатурою у
  власній черзі введення, під час показу не виникає жодної події фокуса, і NVDA про вікно
  мовчить (так було раз із 19 у 0.3.3).
- Не повертати «показати й сховати». До 0.3.3 зі стартом у треї вікно створювалося видимим і
  ховалося за чверть секунди: щоразу блимало, забирало клавіатуру в активної програми, NVDA
  казав «QuickSnippets», а перший показ після цього у 15 випадках із 19 читав із фразами
  «веб-вміст, регіон» і полем пошуку двічі.
- Не показувати вікно звичайного запуску одразу, як до 0.3.3. Вміст отримував клавіатуру, поки
  сторінка ще вантажилася: NVDA читав його з повторами («документ» двічі, «додаток, пробіл»),
  а з новим профілем браузера — через UI Automation.
- Вікно, створене без фокуса, показується без активації, тому після `show()` потрібен
  `set_focus()` (`show_main_window_now`).

Перший сніпет. NVDA, стоячи в полі пошуку, читає сніпет лише тоді, коли той стає вибраним.
Перший список завантажується, ще доки вікно сховане, і перший сніпет у ньому вже вибрано. Тому
до першого показу жоден сніпет не позначається вибраним (`markedIndex` в `App.tsx`): позначка
з'являється разом із показом, як і під час кожного наступного показу, бо ховання знімає вибір.
Дві спроби, які не спрацювали. Зняти вибір під час самого показу: знятий і повернутий за
кілька мілісекунд, сніпет новим вибраним не вважається, і NVDA мовчить. Зняти вибір після
останнього завантаження списку під час запуску: відповіді на запити приходять не обов'язково в
тому порядку, в якому їх надіслано, і зі збереженим нестандартним сортуванням пізніша відповідь
повертала вибір ще до показу (2 прогони smoke із 2).

### Інші подробиці тесту

- Зміна прапорця через UI Automation (`Set-Toggle`) змушує WebView2 переносити клавіатуру між
  своїми внутрішніми вікнами, й інколи вона лишається на одному з них. Програма має в такому разі
  не ховати вікно, доки воно активне, і за 0,2 с повернути клавіатуру у вміст
  (`src-tauri/src/window_blur.rs`). Це перевіряють чотири кроки після кроків автозапуску: один
  повторює зміну шість разів, другий сам ставить клавіатуру на внутрішнє вікно
  (`Chrome_RenderWidgetHostHWND`), третій і четвертий перевіряють, що вікно таки ховається,
  коли активним стає інше вікно.
- Пошук і діалог пароля скидаються лише тоді, коли вікно справді ховається: перед цим Rust
  надсилає вмісту подію `window:hidden`. Звичайна втрата фокуса (подія `blur` у вмісті) нічого
  не скидає. Два кроки в частині про пошук ставлять клавіатуру на внутрішнє вікно із запитом
  у полі пошуку і з відкритим діалогом пароля й перевіряють, що все лишилося на місці.

Запускайте після змін у capabilities, плагінах, фокусі, діалогах чи оголошеннях для екранного диктора.

## Розмір exe

Release-профіль у `src-tauri/Cargo.toml` налаштований на мінімальний розмір:
`opt-level = "z"`, `lto = true`, `codegen-units = 1`, `panic = "abort"`, `strip = true`.
У `src-tauri/tauri.conf.json` увімкнено `build.removeUnusedCommands`: Tauri не вбудовує
команди плагінів, які не дозволені в `capabilities/`. Тому не додавайте туди дозволи
плагінів, яких фронтенд не викликає: глобальна клавіша й буфер обміну працюють з Rust.
Автозапуск програма пише в реєстр сама (`src-tauri/src/autostart.rs`), без плагіна.

Також на розмір впливають:
- `src-tauri/icons/icon.ico` вбудовується в exe. Генеруйте його через
  `npx tauri icon <png 1024×1024>` — так шари зберігаються стисненими (PNG).
- Кожна залежність у `Cargo.toml`. Перевірка невикористаних: `cargo machete` у `src-tauri`.

## Release Process

### Version management

Версія записана в трьох місцях, їх треба тримати однаковими
(`just final-checks` це перевіряє):

```
src-tauri/Cargo.toml        ← [package].version (вбудовується в exe)
src-tauri/tauri.conf.json   ← "version"
package.json                ← "version"
```

### Git Flow release procedure

```powershell
# 1. Гілка релізу від develop
git flow release start 1.2.3

# 2. Підняти версію в трьох файлах, оновити CHANGELOG.md, закомітити
git add src-tauri/Cargo.toml src-tauri/Cargo.lock src-tauri/tauri.conf.json package.json package-lock.json CHANGELOG.md
git commit -m "chore: bump version to 1.2.3"

# 3. Завершити реліз (злиття в main і develop)
git flow release finish 1.2.3

# 4. Запушити гілки (теги не пушити: тег створює release workflow)
git push origin main develop
```

Чекати CI після push не треба: на push він не запускається. Lint і тести на чистій
машині проганяє сам Release workflow перед збіркою (див. нижче).

### Створення GitHub Release

Реліз створюється вручну через GitHub Actions:

1. **Actions → Release → Run workflow** (гілка `main`)
2. Вказати версію (формат `1.2.3`, без `v`)
3. За потреби позначити як pre-release

Workflow автоматично:
1. Збирає фронтенд і запускає `npm run lint`, `npm run test`, `npm run test:rust`.
   Якщо перевірка падає, workflow зупиняється: тегу і релізу немає
2. Запускає `npx tauri build --no-bundle` (фронтенд + Rust binary)
3. Пакує `quick-snippets.exe`, `LICENSE`, `README.md` у ZIP
   `quick-snippets-{version}-windows-x64.zip`
4. Створює файл `quick-snippets-{version}-windows-x64.zip.sha256`
5. Створює і пушить тег `v{version}`
6. Публікує GitHub Release з обома файлами

### Пробний запуск Release (dry run)

Прапорець **dry run** проганяє перевірки, збірку і пакування ZIP, але пропускає
тег і GitHub Release. Ним перевіряють зміни в `release.yml` або готовність гілки
до релізу. Запускати можна з будь-якої гілки, де є цей прапорець:

```powershell
gh workflow run release.yml --ref feature/my-branch -f version=0.0.0..dryrun -f dry_run=true -f prerelease=true
```

Версія `0.0.0..dryrun` — страховка: git не прийме таку назву тегу, тож навіть якщо
прапорець через помилку не спрацює, тег і реліз не з'являться. Справжній реліз
не можна створювати для перевірки навіть тимчасово: Excavator у scoop-bucket бере
найновіший реліз і роздав би його користувачам Scoop.

### Оновлення Scoop

Маніфест `bucket/quick-snippets.json` живе в репозиторії
[ruslan-rv-ua/scoop-bucket](https://github.com/ruslan-rv-ua/scoop-bucket) і оновлюється
там воркфлоу **Excavator**. Він сам знаходить новий реліз (`checkver`), бере хеш з
`.sha256`-файлу (`autoupdate`) і комітить маніфест.

Після релізу:
- або запустіть **Actions → Excavator → Run workflow** у scoop-bucket, щоб оновити одразу;
- або нічого не робіть: Excavator щодня запускається за розкладом.

Тому імена файлів релізу мають залишатися саме такими:

```
https://github.com/ruslan-rv-ua/quick-snippets/releases/download/v{version}/quick-snippets-{version}-windows-x64.zip
https://github.com/ruslan-rv-ua/quick-snippets/releases/download/v{version}/quick-snippets-{version}-windows-x64.zip.sha256
```

Дані користувача (`quick-snippets-data/`) Scoop зберігає між оновленнями через `persist`.

Дані вбудованого браузера WebView2 (кеш і його власний стан) лежать поза нею, у
`quick-snippets-webview/` поруч з exe (`paths::get_webview_data_dir`, `data_directory` у `setup`
у `src-tauri/src/lib.rs`). У `persist` вони не входять і не мають входити: це лише кеш. Під Scoop
вони лежать у теці кожної версії, після оновлення браузер починає з порожнього кешу, а
`scoop cleanup` видаляє їх разом зі старою версією. Без `data_directory` Tauri кладе профіль
браузера в `%LOCALAPPDATA%\com.quicksnippets.app`, спільний для всіх копій програми на комп'ютері.
Так робили версії до 0.3.3 включно. Ту теку програма не читає, не змінює й не видаляє: нею можуть
користуватися старіші копії, а прибрати її вирішує користувач (TASK-27).

## CI

`.github/workflows/ci.yml` запускає `npm run build`, `npm run lint`, `npm run test`,
`npm run test:rust` лише для pull request (репозиторій публічний, тож чужі зміни
перевіряються) і вручну: **Actions → CI → Run workflow** або
`gh workflow run ci.yml --ref <гілка>`.

На кожен push у `develop`/`main` CI не запускається. Ті самі перевірки виконуються
локально в кожній задачі (`npm run test:all`, `npm run lint`), а на чистій машині —
у Release workflow перед збіркою релізу.

## TDD та безпека

- Пишіть тести перед фічами.
- Rust-тести для БД використовують in-memory SQLite (`Connection::open_in_memory()`).
- Критичний інваріант безпеки: розшифрований текст сніпетів НІКОЛИ не передається у фронтенд
  і не потрапляє в логи (зокрема CI). Розшифрування і копіювання в буфер обміну відбуваються
  лише в Rust (`activate_snippet`).

## Troubleshooting (Windows)

- Помилки лінкера під час `cargo build` — зазвичай не встановлено workload "Desktop development with C++".
- `cargo`/`rustup` не в PATH — перезапустіть PowerShell після встановлення.
- Попередження Git про LF/CRLF — нормальні; за потреби налаштуйте `core.autocrlf`.
- Розбіжності версій Tauri/Node/Rust — `npm ci` і `rustup update`.
